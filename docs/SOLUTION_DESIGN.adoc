
= Solution Design: Preppie the Prepper


== Overview
Preppie is a Microsoft Teams-friendly AI agent that joins meetings as a real-time participant, listens to conversations using speech-to-text transcription with speaker diarization, and converts conversation into structured Azure DevOps backlog items. She is built with Azure AI Foundry, Graph Communications API, Azure Speech Services, and deploys via GitHub Actions. The entire solution is fully defined as code.


== Architecture

**Current Implementation** (November 2025):
* Azure Functions Backend (Python 3.11 on Linux) - 9 HTTP endpoints for Azure DevOps
* AI Foundry Agent (Preppie) in East US 2 with GPT-4o
* Function calling pattern - application code handles Preppie's function calls
* Teams Media Bot (C# .NET 8) - **Deployed** on Windows VM (preppie-vm-prod)
* Calling endpoints (/api/calling, /api/calling/media) - **Deployed** for Graph Communications
* Azure Speech Services integration - **Implemented** (ConversationTranscriber with diarization)

==== ServiceHostedMedia vs ApplicationHostedMedia

Microsoft Graph Communications offers two distinct media modes:

[cols="1,2,2"]
|===
|Aspect |ServiceHostedMedia |ApplicationHostedMedia

|**Media Location**
|Microsoft hosts media infrastructure
|Your application hosts media infrastructure

|**Audio Access**
|❌ No access to audio streams
|✅ Full access to RTP audio streams

|**Use Case**
|Meeting presence only (join/leave)
|Real-time transcription, recording, audio injection

|**Complexity**
|Simple - REST API calls only
|Complex - requires native SDK initialization

|**Platform**
|Any platform
|**Windows Server only** (native DLLs)
|===

**Current State**: Bot joins meetings with ServiceHostedMedia (can participate but no audio). Full ApplicationHostedMedia requires SDK integration.

**IMPORTANT**: The `Microsoft.Graph.Communications.Client` is a **stateful SDK** - completely different from the `Microsoft.Graph` REST client. It manages:

* Media platform initialization and lifecycle
* Call state machine (joining, connected, terminating)
* Audio/video socket creation and management
* Generation of the `AppHostedMediaConfig.Blob` (Graph API requires SDK-generated blob, not custom JSON)

==== Why Custom JSON Blob Fails

**Problem**: Attempting to create `AppHostedMediaConfig.Blob` manually with custom JSON results in Graph API error 9999 ("Unknown internal server error").

**Root Cause**: The blob is not simple JSON - it's a binary-encoded configuration generated by the Media Platform SDK during initialization. It contains:

* Audio socket endpoint bindings
* Certificate fingerprints for DTLS
* Media session configuration
* Platform-specific binary headers

**Solution**: Let the SDK initialize the media platform, which generates the correct blob format automatically.

==== Media Platform Initialization Flow

**IMPORTANT**: `MediaPlatform` is a **static class** in `Microsoft.Skype.Bots.Media`. Do not instantiate it.

[source]
----
1. Application Startup (Program.cs)
   ↓
2. Create MediaPlatformSettings with nested MediaPlatformInstanceSettings:
   - ApplicationId
   - MediaPlatformInstanceSettings:
     * CertificateThumbprint (looked up from Windows store)
     * ServiceFqdn (VM's public FQDN)
     * InstancePublicPort / InstanceInternalPort
     * InstancePublicIPAddress
   ↓
3. Initialize static MediaPlatform:
   MediaPlatform.Initialize(settings)  // Static method, NOT new MediaPlatform()
   ↓
4. When joining meeting, create AudioSocket and generate blob:
   var audioSettings = new AudioSocketSettings { ... };
   var audioSocket = new AudioSocket(audioSettings);  // Single argument
   JObject mediaConfig = MediaPlatform.CreateMediaConfiguration(audioSocket);  // Static method
   string blob = mediaConfig.ToString();
   ↓
5. Graph API call with AppHostedMediaConfig.Blob = blob
   ↓
6. RTP packets arrive on UDP ports (50 frames/sec, 20ms each)
   ↓
7. AudioSocket.AudioMediaReceived event fires
   ↓
8. Audio buffers sent to SpeechTranscriptionService
   ↓
9. On shutdown: MediaPlatform.Shutdown()  // Static method
----

=== 2. Azure Speech Services (Real-time Transcription)
**API**: MeetingTranscriber API with speaker diarization

**Capabilities**:

* Real-time speech-to-text transcription
* Speaker identification by name (not just GUEST1, GUEST2)
* Handles multiple speakers with distinct attribution
* Outputs structured transcript with timestamps and speaker labels

**Audio Requirements**:

* **Microphone volume**: Must be adequate (RMS > 100 in audio analysis logs)
* RMS ~15-50 = near silence (will not produce transcription)
* RMS ~100-300 = normal speech (good transcription)
* RMS >500 = loud speech
* Ensure microphone is not muted and correct device is selected in Teams

**Limitations**:

* When speakers overlap (talk simultaneously), audio is clubbed as single speaker
* Requires clear audio quality for accurate diarization


=== 3. Azure AI Foundry Agent (Preppie's Intelligence)
**Model**: GPT-4o (temperature: 0.1 for consistent structured output)

**Region**: East US 2 (AI Foundry Agents feature availability)

**Backend Region**: UK South (Azure Functions closer to Azure DevOps)

**Why GPT-4o**:
* 100% reliable structured outputs for JSON schema compliance
* 5.5x faster than GPT-4 Turbo (109 vs 20 tokens/sec)
* 50-70% cheaper ($3 input, $10 output per 1M tokens)
* Superior function calling for MCP tool integration
* 128K token context window for entire meeting transcripts

**System Prompt**: Defined in `agent-config.json`

**Core Behaviors**:

* Listen to real-time transcription stream
* Identify business requirements, features, and user stories from conversation
* Apply T-Minus-15 methodology (Epic > Feature > User Story > Acceptance Criteria)
* Detect ambiguity and formulate clarifying questions
* Generate speaker-attributed work items
* Decide when to create vs. update work items
* Post real-time notifications to Teams chat

**Tools Available** (via Azure Functions Backend):

* `read_projects` - List all 26 client projects in DevOps organization
* `read_teams` - List teams within a specific project
* `read_work_item` - Get single work item with full details (by ID)
* `read_work_items` - Get multiple work items with flexible filtering (by IDs, parentId with recursive depth, type, state)
* `read_work_item_types` - Discover available work item types for a project
* `read_link_types` - Discover available link types (Parent, Child, Related, Dependency, Duplicate)
* `search_work_items` - WIQL-based search with advanced filtering
* `create_work_item` - Create Epics, Features, Stories, Questions
* `link_work_items` - Create flexible work item links with custom link types (not just parent-child)


=== 4. Azure Functions Backend (DevOps Integration)
**Technology**: Azure Functions (Python 3.11) with Azure DevOps REST API

**Deployment**: Serverless compute on Azure Functions Consumption Plan (Y1)

**Function App Name**: `pennie-backend-prod`

**Available Functions** (Standardized CRUD Naming):

* `read_projects` (GET /api/read_projects) - List all client projects in KnowAll organization
** Returns: Project ID, name, description, state, visibility
** Use case: Preppie discovers available client projects dynamically

* `read_teams` (POST /api/read_teams) - List teams in a specific project
** Parameters: `project` (project name or ID)
** Returns: Team ID, name, description
** Use case: Team-specific work item routing

* `read_work_item` (POST /api/read_work_item) - Get single work item with full details
** Parameters: `project`, `workItemId`
** Returns: All fields, relations, comments, attachments
** Use case: Logic App reads specific Epic for document generation

* `read_work_items` (POST /api/read_work_items) - Get multiple work items with flexible filtering
** Parameters: `project`, `workItemIds` (optional array), `parentId` (optional), `depth` (1-5, default 1), `workItemType` (optional), `state` (optional), `top` (default 100, max 200)
** Returns: Array of work items with depth level indicator (`_depth` field)
** Use cases:
*** Get specific IDs: `{"project": "ClientA", "workItemIds": [123, 456]}`
*** Get direct children: `{"project": "ClientA", "parentId": 123}` (Epic -> Features)
*** Get nested hierarchy: `{"project": "ClientA", "parentId": 123, "depth": 3}` (Epic -> Features -> Stories)
*** Filter by type: `{"project": "ClientA", "parentId": 123, "workItemType": "Feature"}`
** **Recursive depth support**: depth=1 (direct children), depth=2 (children + grandchildren), up to depth=5

* `read_work_item_types` (POST /api/read_work_item_types) - Get available work item types
** Parameters: `project`
** Returns: Array of work item types with name, description, icon, color
** Use case: Preppie discovers what types are configured (Epic, Feature, User Story, Bug, etc.)

* `search_work_items` (POST /api/search_work_items) - WIQL-based advanced search
** Parameters: `project`, `workItemType` (optional), `state` (optional), `assignedTo` (optional), `tags` (optional), `titleContains` (optional), `top` (default 50)
** Returns: Array of work items matching all specified filters
** Use case: Find all Active Features assigned to a user, or search by title keywords

* `create_work_item` (POST /api/create_work_item) - Create new work items
** Parameters: `project`, `workItemType` (Epic/Feature/User Story/Question), `title`, `description`, `acceptanceCriteria`, etc.
** Returns: Created work item ID and URL
** Use case: Preppie creates backlog items from meeting transcripts

* `read_link_types` (GET /api/read_link_types) - Get available link types
** Parameters: None required
** Returns: Array of link types with name, display name, description, direction, category
** Link categories: hierarchy (Parent/Child), dependency (Predecessor/Successor), related, other (Duplicate)
** Use case: Preppie discovers what link types are available

* `link_work_items` (POST /api/link_work_items) - Create flexible work item links
** Parameters: `project`, `sourceId`, `targetIds` (array), `linkType` (optional, defaults to Hierarchy-Forward), `comment` (optional)
** **Backward compatible**: Also accepts legacy `parentId`/`childIds` parameters (maps to Hierarchy-Forward)
** Returns: Success status for each link with link type
** Link types supported:
*** `System.LinkTypes.Hierarchy-Forward` - Parent → Child (default)
*** `System.LinkTypes.Hierarchy-Reverse` - Child → Parent
*** `System.LinkTypes.Related` - Related work items
*** `System.LinkTypes.Dependency-Forward` - Predecessor → Successor
*** `System.LinkTypes.Dependency-Reverse` - Successor → Predecessor
*** `System.LinkTypes.Duplicate-Forward` - Duplicate item
** Use cases:
*** Maintain Epic > Feature > Story hierarchy
*** Create task dependencies (must complete X before Y)
*** Link related work items
*** Mark duplicates

**Authentication**: Personal Access Token (PAT) stored in Azure Function App settings

**Dynamic Multi-Client Support**: All functions accept `project` parameter for per-client project selection (26 client projects supported)

**Naming Convention**: Standardized CRUD operations:
* `read_*` - Retrieve data (GET operations)
* `create_*` - Create new items (POST operations)
* `link_*` - Create relationships (POST operations)

**Integration**: Azure AI Foundry Agent calls functions via HTTP (function-level auth)

**Benefits**:

* Serverless - no infrastructure to manage
* Standardized naming convention (CRUD-based)
* Dynamic project selection (per-client support)
* Direct Azure DevOps REST API integration
* Custom logic for T-Minus-15 methodology
* Supports both real-time agent actions and Logic App document generation

== System Prompt & Behavioral Guidelines

Preppie's prompt is defined in `agent-config.json` and instructs her to:

* Act as a skilled business analyst
* Listen passively to meeting conversation (audio transcription)
* Apply T-Minus-15 methodology for structuring backlog items
* Ask clarifying questions in Teams chat when requirements are ambiguous
* Tag work items with speaker attribution and timestamps for traceability
* Post change notifications with links to created DevOps items
* Batch related changes (within 30 seconds) to reduce chat noise
* Never hallucinate - always use tools to fetch real DevOps data


== T-Minus-15 Methodology Integration

**Hierarchy**:

* Epic > Feature > User Story > Question

**Metadata Captured**:

* Speaker name and timestamp (from MeetingTranscriber)
* Meeting ID and date
* Originating conversation context
* Parent-child relationships
* Value statements and acceptance criteria (Given/When/Then format)

== Security & Compliance


=== Data Residency

**Regional Deployment Strategy**:

**Current Multi-Region Deployment**:
* **East US 2**: AI Foundry Agent (Preppie with GPT-4o) - Agents feature availability
* **UK South**: Azure Functions Backend, Storage, Application Insights - DevOps proximity

**Future Single-Region Architecture** (when all components deployed):
* **Target Region**: UK South or other region based on data residency requirements
* **Components**: Windows Server VM (Teams Media Bot), Azure Speech Services, AI Foundry Agent, Azure Functions Backend, Storage, Application Insights

**Multi-Region Considerations** (Current):
* Agent in East US 2 (only region with Agents feature at deployment time)
* Backend in UK South (closer to Azure DevOps for lower latency)
* Minimal cross-region traffic (only function call requests/responses)

**Single-Region Architecture Benefits** (Future):
* All data processing within chosen region for complete data residency
* No cross-region latency - optimal performance
* Simplified compliance and data governance
* Lower egress costs (no inter-region data transfer)

**Data Minimization**:
* Only conversation segments requiring analysis sent to AI Foundry
* Structured work items (summaries) stored in Azure DevOps UK South
* Raw meeting audio processed entirely in UK South (never leaves region)
* No external third-party services required


=== Authentication & Authorization

* Managed Identity for service-to-service authentication (Functions ↔ DevOps, Functions ↔ AI Foundry)
* Azure DevOps PAT stored in Key Vault (fallback to Managed Identity where possible)
* Bot credentials stored in Key Vault
* Graph API permissions granted via admin consent


=== Audio & Transcript Security

* Audio streams processed in real-time, not recorded or stored
* Transcripts stored temporarily in AI Foundry agent memory (session-scoped)
* Optional: Persistent transcript storage in Azure Storage (encrypted at rest)
* Speaker attribution data treated as sensitive metadata


=== Compliance

* GDPR compliant (data residency in EU, right to deletion)
* Meeting participants must consent to bot joining and transcribing
* Bot announces presence when joining meeting
* Transcription status visible to all participants

== Scalability Considerations


=== Current Design (MVP)

* Single Windows VM handles one bot instance
* Bot can join one meeting at a time
* Suitable for internal KnowAll AI team usage


=== Future Scaling (Multiple Concurrent Meetings)

* Deploy multiple Windows VM instances in VMSS (Virtual Machine Scale Set)
* Load balancer to distribute meeting join requests
* Horizontal scaling based on active meeting count
* Kubernetes cluster (AKS with Windows node pools) for containerized bot instances
