== Overview

This document provides comprehensive deployment instructions for Pennie the Prepper, including environment setup, deployment automation, and operational procedures for DEV / TEST / PROD lifecycle management.

**NOTE**: This guide describes the future Teams Media Bot architecture. Current deployment uses Azure Functions backend (see warning above).

== Architecture Summary

Pennie deploys as a single-region solution with the following components:

* **Windows Server VM**: Hosts Teams Media Bot (C#) with function call handler - **FUTURE PHASE**
* **Azure Functions Backend**: Python 3.11 on Linux - **CURRENTLY DEPLOYED**
* **Azure AI Foundry**: Hosts Pennie agent with GPT-4o model - **CURRENTLY DEPLOYED in East US 2**
* **Azure Speech Services**: Real-time transcription with speaker diarization - **FUTURE PHASE**
* **Azure DevOps**: Work item management (Epics, Features, Stories, Questions)
* **Application Insights**: Monitoring and diagnostics
* **Azure Storage**: Logs and operational data
* **Key Vault**: Secrets management

**Current Deployment**: Azure Functions backend + AI Foundry agent (manual testing via playground)
**Future Deployment**: Windows VM with Teams Media Bot for real-time meeting integration

== Environment Strategy

=== Overview

Pennie supports three deployment environments aligned with software development lifecycle best practices:

|===
|Environment |Purpose |Azure Resources |Teams Integration |DevOps Project

|**DEV** |Development and feature testing |Shared Dev subscription or resource group |Test Teams tenant or isolated test meetings |DevOps **Test** project
|**TEST/Staging** |Pre-production validation and UAT |Staging resource group in production subscription |Test Teams tenant or isolated test meetings |DevOps **Staging** project
|**PROD** |Live production usage |Production resource group (`TMinus15Agents`) |Production Teams tenant (KnowAll AI) |DevOps **Production** project
|===

=== DEV Environment

**Purpose**: Rapid development iteration and unit/component testing

**Deployment**:
* Lightweight deployment (can use local Bot Framework Emulator instead of full VM)
* Shared Azure subscription with resource group per developer (optional)
* Mock Teams meetings using Bot Framework Emulator
* Real Azure Speech Services (dev instance) for transcription testing
* Real Azure DevOps Test project for work item validation

**Configuration**:
* `.env.dev` - Development-specific environment variables
* `agent-config.dev.json` - Lower cost model (GPT-4o-mini for testing)
* Logging: `DEBUG` level for verbose output

**Access**:
* Developer workstations (local development)
* No public internet access required (uses emulator)

**Cost**: Minimal (~$10-30/month) - primarily Speech Services usage

**Testing Approach**:
* Unit tests with mocked dependencies
* Component tests with real Speech/DevOps APIs
* Simulated Teams meetings (Bot Framework Emulator)
* No live meeting testing in DEV

=== TEST Environment (Staging)

**Purpose**: Pre-production validation, integration testing, UAT

**Deployment**:
* Full infrastructure deployed via Bicep (identical to PROD)
* Separate Windows VM in staging resource group
* Isolated Azure AI Foundry project for staging
* Real Azure Speech Services (staging instance)
* Azure DevOps **Staging** project (separate from production)

**Configuration**:
* `.env.test` - Test-specific environment variables
* `agent-config.test.json` - Same model as PROD (GPT-4o)
* Logging: `INFO` level

**Access**:
* Test Teams tenant (if available) or production tenant with test meetings
* QA team has access
* Developers can deploy to TEST for validation

**Cost**: Moderate (~$100-250/month) - full infrastructure but lower usage

**Testing Approach**:
* Full integration test suite
* End-to-end live meeting tests with test participants
* User acceptance testing (UAT) with stakeholders
* Performance and load testing

**Promotion Gate**:
* All integration tests passing
* UAT sign-off from product owner
* No critical bugs outstanding
* Security review completed

=== PROD Environment

**Purpose**: Live production usage for KnowAll AI internal meetings

**Deployment**:
* Full infrastructure deployed via Bicep (production-grade)
* Production Windows VM in `TMinus15Agents` resource group
* Azure AI Foundry Hub: `knowall-ai-foundry` (existing)
* Azure Speech Services (production instance)
* Azure DevOps **Production** project

**Configuration**:
* `.env.prod` (stored in Azure Key Vault, not Git)
* `agent-config.json` - Production model (GPT-4o)
* Logging: `INFO` level (WARNING for sensitive components)

**Access**:
* Production Teams tenant (KnowAll AI)
* Real client and internal meetings
* Restricted access (only deployment pipeline can deploy)
* Operations team has read-only access for monitoring

**Cost**: Full (~$110-270/month) based on meeting frequency

**Monitoring**:
* Application Insights with alerting
* Daily log review for errors
* Weekly work item quality metrics review

**Disaster Recovery**:
* Daily automated backups of agent configuration
* Infrastructure as Code (Bicep) for rapid rebuild
* Work items stored in Azure DevOps (Microsoft-managed backup)

== Deployment Lifecycle

=== Branching Strategy

[source]
----
main (PROD)
  ↑
  merge via PR
  |
develop (TEST)
  ↑
  merge via PR
  |
feature/ABC-123 (DEV)
----

**Branches**:
* `main` - Production-ready code, deploys to PROD
* `develop` - Integration branch, deploys to TEST
* `feature/*` - Feature branches for development (local DEV testing)

**Pull Request Requirements**:
* All unit tests passing
* Code review from 1+ team member
* No linting errors
* Coverage ≥80% for new code

=== Deployment Pipeline

==== Local DEV Deployment

**Trigger**: Manual, developer workstation

**Steps**:
1. Developer writes code on `feature/ABC-123` branch
2. Run unit tests locally: `pytest tests/unit/`
3. Run component tests: `pytest tests/component/`
4. Test with Bot Framework Emulator (simulated meetings)
5. Validate work items created in DevOps Test project
6. Commit and push to feature branch

**No automated deployment to cloud for DEV**

==== TEST Environment Deployment

**Trigger**: Push to `develop` branch or manual dispatch

**Workflow**: `.github/workflows/deploy-test.yml`

**Steps**:

1. **Pre-Deployment Validation**
   - Checkout `develop` branch
   - Run unit tests (`pytest tests/unit/`)
   - Run component tests (`pytest tests/component/`)
   - Fail deployment if tests fail

2. **Infrastructure Deployment**
   - Azure login (Service Principal for TEST)
   - Deploy Bicep templates to TEST resource group
   ```bash
   az deployment sub create \
     --location uksouth \
     --template-file infra/main.bicep \
     --parameters @infra/main.parameters.test.json
   ```
   - Provision: VM, AI Foundry, Speech Services, Storage, Key Vault

3. **Application Deployment**
   - **Windows VM Setup**:
     - Install Node.js 20+ (for MCP server)
     - Install Azure DevOps MCP Server: `npm install -g @azure-devops/mcp`
     - Deploy Teams Media Bot (C# application)
     - Configure MCP server with TEST DevOps credentials
   - **AI Foundry Agent**:
     - Deploy agent from `agent-config.test.json`
     - Configure MCP connection to Windows VM
     - Validate agent can reach MCP server

4. **Post-Deployment Validation**
   - Run smoke tests (`tests/smoke/`)
   - Bot health check endpoint
   - MCP server connectivity test
   - Sample transcript processing test
   - Notify team on Slack/Teams if deployment succeeds

5. **Integration Testing**
   - Automatically run integration test suite
   - Create test work items in DevOps Staging project
   - Cleanup test data after run

**Deployment Duration**: 15-25 minutes

**Rollback**: Redeploy previous successful commit from `develop`

==== PROD Environment Deployment

**Trigger**: Push to `main` branch (after PR merge from `develop`)

**Approval Gate**: Manual approval required before deployment

**Workflow**: `.github/workflows/deploy-prod.yml`

**Steps**:

1. **Pre-Deployment Checks**
   - All tests passing on `develop`
   - UAT sign-off present (GitHub issue linked)
   - Security review completed (checklist in PR)
   - Change notification sent to team (24 hours advance notice)

2. **Manual Approval**
   - GitHub Actions pauses for approval
   - Product owner or tech lead approves deployment
   - Deployment window: Working hours only (Mon-Fri 9am-5pm UK)

3. **Infrastructure Deployment**
   - Azure login (Service Principal for PROD)
   - Deploy Bicep templates to PROD resource group
   ```bash
   az deployment sub create \
     --location uksouth \
     --template-file infra/main.bicep \
     --parameters @infra/main.parameters.prod.json
   ```
   - Updates existing resources (no downtime for infrastructure)

4. **Application Deployment**
   - **Blue-Green Deployment** (if VM already exists):
     - Deploy to new VM (green)
     - Run smoke tests on green VM
     - Switch DNS/routing to green VM
     - Keep blue VM for rollback (24 hours)
   - **First Deployment**:
     - Deploy to single VM
     - Configure all services
     - Run smoke tests

5. **Post-Deployment Validation**
   - Run production smoke tests
   - Verify bot can join test Teams meeting
   - Check Application Insights for errors
   - Monitor for 1 hour post-deployment

6. **Communication**
   - Notify team that deployment is complete
   - Post release notes in Slack/Teams
   - Update status page (if applicable)

**Deployment Duration**: 25-35 minutes (including approval wait time)

**Rollback Plan**:
* If smoke tests fail: Automatically rollback to previous version
* If issues found post-deployment: Manual rollback by redeploying previous commit
* Rollback time: <10 minutes

== Step-by-Step Deployment

=== 1. Clone Repository

```bash
git clone https://github.com/benweeks/GetPenn.ie.git
cd GetPenn.ie
```

=== 2. Configure Environment

```bash
# Copy example environment file
cp .env.example .env

# Edit .env with your Azure details
nano .env
```

**Required values**:
* `AZURE_SUBSCRIPTION_ID` - Your subscription ID
* `AZURE_TENANT_ID` - Your tenant ID
* `AZURE_RESOURCE_GROUP` - Resource group name (e.g., `TMinus15Agents`)
* `AZURE_LOCATION` - Region (e.g., `uksouth`, `eastus2`)
* `AZURE_AI_HUB_NAME` - AI Foundry hub name (will be created if doesn't exist)
* `AZURE_AI_PROJECT_NAME` - AI Foundry project name
* `AZURE_DEVOPS_ORG` - Your DevOps organization name
* `AZURE_DEVOPS_PROJECT` - Your DevOps project name

=== 3. Create Azure AD App Registration (One-Time Setup)

**Purpose**: Teams bot requires an app registration for authentication

**Steps**:

1. **Create App Registration**:
   ```bash
   az ad app create \
     --display-name "Pennie the Prepper Bot" \
     --sign-in-audience AzureADMyOrg
   ```

2. **Save App ID**:
   ```bash
   export TEAMS_APP_ID=$(az ad app list --display-name "Pennie the Prepper Bot" --query "[0].appId" -o tsv)
   echo $TEAMS_APP_ID
   ```

3. **Create Client Secret**:
   ```bash
   az ad app credential reset --id $TEAMS_APP_ID --append
   ```
   - Save the `password` output as `TEAMS_APP_PASSWORD`

4. **Configure API Permissions**:
   - Navigate to Azure Portal → Entra ID → App Registrations → Pennie the Prepper Bot
   - API Permissions → Add a permission → Microsoft Graph → Application permissions
   - Add the following permissions:
     * `Calls.AccessMedia.All` - Access media streams in calls
     * `Calls.JoinGroupCall.All` - Join group calls and meetings
     * `OnlineMeetings.ReadWrite.All` - Read and create online meetings

5. **Grant Admin Consent**:
   - Click "Grant admin consent for [Your Organization]"
   - Confirm consent
   - **Important**: This requires Global Administrator or Privileged Role Administrator role

6. **Update `.env` file**:
   ```bash
   echo "TEAMS_APP_ID=$TEAMS_APP_ID" >> .env
   echo "TEAMS_APP_PASSWORD=<password-from-step-3>" >> .env
   ```

**Deploy Teams Media Bot**:

=== 6. Deploy AI Foundry Agent

**Option A: Automated Deployment Script** (Recommended)

Deploy Pennie agent using the Azure AI Foundry Assistants API:

```bash
# Ensure Azure CLI is logged in
az login
az account set --subscription $AZURE_SUBSCRIPTION_ID

# Run deployment script
./scripts/deploy-agent.sh
```

**What the script does**:
1. Loads configuration from `.env` and `agent-config.json`
2. Retrieves Azure AI Foundry endpoint and access token
3. Creates agent using Assistants API with:
   - GPT-4o model with JSON schema strict mode
   - System instructions from `agent-config.json`
   - Function calling tools for Azure DevOps (wit_create_work_item, wit_add_child_work_items)
4. Tests agent with sample transcript
5. Saves Assistant ID to `.env` as `AZURE_AI_ASSISTANT_ID`

**Expected output**:
```

✅ Model: gpt-4o
```

**Option B: Azure AI Foundry Portal** (Manual)

1. Navigate to Azure Portal → AI Foundry → Your Hub → Projects
2. Create project: "T-Minus-15 Agents" (or use existing)
3. Go to **Assistants** → **Create Assistant**
4. Configure agent:
   - **Name**: Pennie the Prepper
   - **Model**: gpt-4o (deployment: gpt-4o)
   - **Instructions**: Copy from `agent-config.json` → `instructions` field
   - **Temperature**: 0.2

   - **Max Tokens**: 4096

=== Monitoring

* Review work item quality metrics

=== Maintenance

**Routine**:
* Windows VM updates (monthly, scheduled maintenance window)
* MCP server updates: `npm update -g @azure-devops/mcp`
* Bot application updates (via GitHub Actions deployment)
* Certificate renewal (if using custom domain)

**Agent Configuration Updates**:
* Edit `agent-config.json` in repository
* Commit and push to `develop` → TEST environment
* After validation, merge to `main` → PROD deployment
* No VM reboot required (agent reloads automatically)

=== Backup and Recovery

**Automated Backups**:
* Agent configuration: Stored in Git (version controlled)
* Infrastructure: Bicep templates in Git (can rebuild)
* Work items: Azure DevOps managed backup (Microsoft responsibility)
* Logs: Retained in Application Insights (90 days by default)

**Disaster Recovery Procedure**:

1. **VM Failure**:
   - Redeploy infrastructure via Bicep: `az deployment sub create ...`
   - Re-run VM configuration scripts
   - Restore from latest deployment (typically <30 minutes)

2. **Agent Failure**:
   - Redeploy agent from `agent-config.json`
   - No data loss (stateless agent)

3. **MCP Server Failure**:
   - Restart MCP service: `nssm restart PennieMCP`
   - If persistent: Re-authenticate and reinstall

4. **Azure DevOps API Issues**:
   - MCP server automatically retries with exponential backoff
   - Monitor Application Insights for sustained failures
   - If needed: Escalate to Microsoft support

== Troubleshooting

=== Bot Doesn't Join Meeting

**Symptoms**: Bot invited to meeting, but doesn't appear

**Diagnosis**:
```powershell
# Check bot service status
nssm status PennieBot

# Check bot logs
Get-Content C:\Pennie\logs\bot.log -Tail 50

# Check Application Insights
# Portal → AI → Logs → Query:
# traces | where message contains "JoinMeeting"
```

**Common Causes**:
* Graph API permissions not granted (admin consent required)
* Bot app ID or password incorrect (check Key Vault)
* Firewall blocking outbound connections from VM
* Meeting invite not sent correctly (bot must be explicitly invited)

**Resolution**:
* Verify Graph API permissions in Azure AD
* Check `.env` or Key Vault for correct credentials
* Ensure VM NSG allows outbound HTTPS
* Re-invite bot to meeting

=== No Transcription / Work Items Created

**Symptoms**: Bot joins meeting, but no work items created

**Diagnosis**:
```powershell
# Check Speech Services connection
curl https://<SPEECH-RESOURCE>.cognitiveservices.azure.com/

# Check MCP server logs
Get-Content C:\Pennie\mcp\logs\mcp.log -Tail 50

# Check AI Foundry agent logs
# Portal → AI Foundry → Deployments → Logs
```

**Common Causes**:
* Azure Speech Services API key expired or incorrect
* MCP server not running or unreachable
* AI Foundry agent not connected to MCP server
* Audio quality too poor for transcription

**Resolution**:
* Verify Speech Services key in Key Vault
* Restart MCP service: `nssm restart PennieMCP`
* Check MCP endpoint configuration in AI Foundry
* Test with clearer audio (reduce background noise)

=== Work Items Missing Speaker Attribution

**Symptoms**: Work items created, but speaker name is blank

**Diagnosis**:
* Check Azure Speech Services diarization settings
* Review transcript output format

**Common Causes**:
* Speaker diarization not enabled on Speech Services
* Meeting participants not identified by name (showing as "Guest 1", "Guest 2")
* Audio quality too poor for speaker identification

**Resolution**:
* Verify Speech Services has diarization enabled (`speakerDiarization: true`)
* Ensure meeting participants join with authenticated accounts (not anonymous)
* Improve meeting audio quality (use headsets, reduce echo)

=== Duplicate Work Items Created

**Symptoms**: Same requirement mentioned twice, creates two work items

**Diagnosis**:
* Review agent logs for duplicate detection logic
* Check if `GetWorkItems` tool is being called before creation

**Common Causes**:
* Agent not querying existing work items before creating
* Semantic similarity threshold too low
* Multiple speakers mention same requirement with different wording

**Resolution**:
* Update agent instructions to always check existing items
* Tune semantic similarity matching
* Add post-meeting deduplication review step (manual or automated)

== Security Considerations

=== Secrets Management

**Do NOT commit to Git**:
* `.env` file (use `.env.example` as template)
* Personal Access Tokens (PAT)
* Service Principal credentials
* Teams bot app password
* API keys

**Use Azure Key Vault**:
* Store all secrets in Key Vault
* Grant VM Managed Identity access to Key Vault
* Bot and MCP server read secrets at runtime

**Rotate Secrets**:
* Teams bot password: Every 90 days
* Azure DevOps PAT: Every 90 days
* Service Principal credentials: Every 365 days

=== Network Security

**VM Network Security Group (NSG)**:
* Inbound: Allow HTTPS (443) from Teams service IPs only
* Outbound: Allow HTTPS (443) to Azure services
* Block all other traffic

**VNet Integration** (recommended for production):
* Deploy VM in Azure VNet with private subnet
* Use Azure Bastion for secure VM access (no public RDP)
* Private Endpoints for Azure services (AI Foundry, Speech, DevOps)

=== Compliance

**GDPR**:
* Meeting participants must consent to transcription
* Bot announces presence when joining meeting
* Transcripts not stored long-term (real-time processing only)
* Right to deletion: Manually delete work items if requested

**Data Residency**:
* All components in single region (UK South for UK data residency)
* No cross-border data transfer
* Work items stored in Azure DevOps (verify region)

== Rollback Procedures

=== Rollback Triggers

* Smoke tests fail post-deployment
* Critical bug found in production within 24 hours
* Work item quality degrades significantly (manual review)
* Bot cannot join meetings reliably (<90% success rate)

=== Rollback Steps

**Option 1: GitHub Actions Rollback** (Recommended)

```bash
# Revert commit on main branch
git revert HEAD
git push origin main

# This triggers deployment pipeline with previous version
```

**Option 2: Manual Rollback**

1. **Identify Last Good Commit**:
   ```bash
   git log --oneline
   # Find last successful deployment commit
   ```

2. **Deploy Previous Version**:
   ```bash
   git checkout <last-good-commit>
   az deployment sub create \
     --location uksouth \
     --template-file infra/main.bicep \
     --parameters @infra/main.parameters.prod.json
   ```

3. **Verify Rollback**:
   ```bash
   pytest tests/smoke/ --env=prod
   ```

**Option 3: Blue-Green Swap**

If blue-green deployment was used:
```bash
# Switch back to blue VM (previous version)
az vm start --name pennie-vm-blue --resource-group TMinus15Agents
az network traffic-manager endpoint update \
  --name pennie-endpoint \
  --profile-name pennie-traffic \
  --type azureEndpoints \
  --target-resource-id /subscriptions/.../pennie-vm-blue
```

=== Post-Rollback Actions

* Investigate root cause in logs
* Create incident report
* Fix issue in `develop` branch
* Redeploy to TEST for validation
* Schedule new PROD deployment when ready
